# 更新確認のタイムアウト修正（0.82.0）

## 対象と原因

発案者から、Pixel 6aのChromeとiPhone XRのChromeで、通常のページは開けるがゲーム内メニューの更新確認が時間切れになるとの報告を受けた。表示中の版番号と正確なエラー全文は未取得。端末実機での原因の特定と、PCで再現した実装上の原因は区別する。

0.81.0では、短い状態確認と資材の取得・保存の両方に5秒の応答期限を使っていた。更新時は既存画像が同じでも全75資材（約29.32 MiB）を取得し直し、欠損が1件だけでも全件を取り直す。新しい配信の準備にも30秒の期限があった。通常表示は保存済み資材を利用できるため、ページが開けることだけではこの処理の成功を判断できない。

実際の0.81.0の画面側コードと配信用Workerを使い、保存資材を1件だけ不足させ、その通信を6.5秒へ遅延させた。応答は正常に返る設定でも、約5.1秒で「準備の確認に応答がありません」となった。公開側の版情報とWorkerは調査時点で約0.28秒・約0.12秒で応答していた。認証の問題や端末故障とは断定せず、確認できたアプリ側の短い期限と重複取得を修正する。

## 修正

- 資材の準備・インストール待ちは120秒とする。短い状態確認は5秒、版情報の取得は10秒、更新適用は10秒を維持する。120秒は各待機の期限であり、更新全体の最大所要時間ではない。
- 保存済み資材の一覧を一度で調べ、不足分だけを補う。複数操作が重なっても準備は1回にまとめ、失敗時も開始済みの処理が終わるまで同じ準備を共有する。
- 新旧の配信情報にあるSHA-256（ファイル内容の照合値）が一致する資材は、同じ公開範囲にある旧版の保存から再利用する。保存された本文の照合も行い、不一致なら通信で取り直す。新規取得の本文も照合する。
- 再利用時は旧版の応答URLを引き継がない。モジュールの相対参照が旧版へ戻るのを防ぎ、本文・形式・状態を保った応答を作る。
- 通信は最大4件ずつ、1件の取得は本文の受信を含め60秒まで。失敗時は新たな取得を始めず、取得済み部分と旧版を保持して再試行できるようにする。
- 確認中の説明に、資材の取得・保存を待っていることを表示する。表示版と読み込みの版を0.82.0へ更新する。

更新を適用するかは従来どおり利用者が選ぶ。旧版の資材、成績、保存回路を削除しない。ゲームの42面・288出題、計算、採点、音、配置、保存形式は変更しない。旧版とのメッセージ形式も維持する。

## ローカル検証

| 検証 | 結果 |
| --- | --- |
| 修正前の6.5秒通信 | 0.81.0で約5.1秒後に時間切れを再現 |
| 修正後の同じ通信 | Chromium約6.69秒・WebKit約6.87秒で準備完了、エラーなし |
| 自動テスト | 全34ファイル合格。構文98ファイル合格 |
| 更新・資材の重点テスト | 16件合格。遅い準備、破損した旧資材、新取得の不一致、並行準備と途中失敗を含む |
| 実際の0.78.0から更新 | Chromium・WebKitの通常メニューと登録の復旧、計10項目合格 |
| 実際の0.81.0から更新 | 同10項目合格 |
| 通信なしの起動と操作 | 両ブラウザ計28項目合格。帰還25面・鏡31面・開閉37面・複合42面の満点、鏡操作等を含む |
| ビルドと公開版比較 | 0.82.0・75資材の生成、両公開先の0.81.0からの版更新検査が合格 |

旧版のソースを実際に取り出して配信し、保存した成績と回路が更新後も同一であることを確認した。メニューからの更新で変更のない大きな画像・書体18件の再取得を避け、取得量は0.78.0から約0.59 MB、0.81.0から約0.49 MBだった。初回起動で旧資材がない場合には全資材の通信が必要になる。

WebKitの登録解除・再起動検査では、登録の列挙が空でも制御中のWorkerが存在する状態が出た。実際の旧0.81.0でも同じ状態を再現したため、新実装の不具合とはしない。検査補助は、制御中Workerの版・準備完了応答・全資材の存在も確認する方式とし、アプリ側の登録仕様は変更していない。

古い`check_offline_features.cjs`は3段階だったチュートリアルを前提としており、現在の4段階と一致せず途中で失敗した。これを合格とは扱わない。現在の通信なし起動・操作は、現行の`check_extension_sets.cjs --offline`と旧版更新検査で確認した。

## 証拠

- `設計検証/check_update_timeout.cjs`：実配信用コードによる低速通信の再現。
- `設計検証/更新待ち時間/0.81.0/chromium/report.json`：修正前の再現。意図した失敗の記録。
- `設計検証/更新待ち時間/0.82.0/{chromium,webkit}/report.json`：同条件での成功。
- `設計検証/旧版更新/from-0.78.0/report.json`、`from-0.81.0/report.json`：実際の旧版からの更新・保存保持。
- `設計検証/三つのテーマ/0.82.0/offline/{chromium,webkit}/report.json`：現行の通信なし検査。

## 公開・実機の確認

別担当の読み取り専用レビューでは、今回の更新処理・テスト・検査補助にCritical／Important／Minorの指摘はなかった。試験の再実行と公開・実機結果の判定はレビュー担当の対象外であり、上記の実行結果と分けて扱う。

2026-10-22（日本時間）、0.82.0を両URLへ公開し、確認を完了した。

- 配信元：`1ed9043adb8f194d4714eeec0f3b0cbc541a6588`。
- GitHub Actions：[39696401715](https://github.com/gerupon-lgtm/prism/actions/runs/39696401715)。build・deployが成功。
- Cloudflare：`9205df72-9a1f-48f5-b422-ff765e4a4c77`。`github:push`で自動起動し、ビルドと配信が成功。全34テストと75資材の生成も配信ログで確認した。今回の手動配信は行っていない。
- [独自ドメイン](https://prism.sikumilab.com/)と[従来のGitHub Pages](https://gerupon-lgtm.github.io/prism/)で各88項目、計176項目が合格。全資材の形式とSHA-256、版と配信元、起動時の自動確認、タイトルの概要・ハンバーガーメニューからの手動確認、縦横の配置、結線・2.5秒100点、保存・書き出し、HTTPキャッシュを消してページを閉じた後の通信なし再起動を確認した。
- 証拠：`設計検証/更新待ち時間/0.82.0/{prism.sikumilab.com,gerupon-lgtm.github.io}/public/report.json`。

先のGitHub連携復旧後、今回の本体変更でpushによるCloudflare自動配信も確認できた。資料と検証結果だけの追記では、同版を再配信しない。

PCのChromium・WebKitによる検査であり、Pixel 6a・iPhone XRの実機改善を確認したとは扱わない。更新のためにアンインストールやサイトデータの削除を求めない。旧画面には従来の短い期限が残るため、最初の確認だけ時間切れになる可能性は残る。準備済みの新版を適用して0.82.0へ切り替えた後、同じメニューでの改善を実機確認する。
