# 0.24.0からの更新と登録解除による復旧

## 経緯と訂正

発案者はPixel 6aのChrome、0.24.0で更新確認が正常に働かないと報告した。旧版で更新が動かないという報告に対し、同じメニュー操作を案内してしまったことを訂正する。

0.26.0の既存PWA検証は修正版のソースへ合成の後続版番号を付けた資材であり、問題のある0.24.0のソースからの移行証拠ではなかった。公開URLの確認も新規状態からの0.26.0であり、この境界を維持する。実機の旧版で更新できるとは断定しない。

## 確認したこと

設計検証/check_legacy_update.cjsはコミット2a17b65b47e169b015b30e53c221786a0af9b027から0.24.0のsrc/public/フォント/index/package/ビルド処理を取り出し、その原本をビルドする。現在のソースの版番号だけを書き換えたものではない。現在の公開相当0.26.0の資材へ切り替える同じ/prism/配信元で検証する。利用者のプロフィール・実データは使わない。

- PC Chromium/WebKitで、実際の旧版メニューから新版の準備・適用ができる正常経路を確認した。これをPixelでの報告の否定や解消確認にしない。
- PC Windows Chromeでは、旧版で100点の成績を登録し自由回路を保存した後、sw.js取得を503にする合成の失敗を起こす。旧版の更新画面から移行できない状態を確認する。この503をPixelの原因と扱わない。
- 配信を正常に戻した後、実際のchrome://serviceworker-internals/の対象ScopeだけのUnregisterリンクで登録を解除する。CacheStorage・保存回路・成績が残ることを照合する。旧画面を閉じ、通常HTTPキャッシュも残したまま?recover=0.26.0の新しいURLから再起動すると0.26.0になる。アンインストール・サイトデータ消去・保存領域初期化を使わない。
- 復旧は、未保存回路と実行記録を先に保存・書き出しし、対象の登録だけを解除してアプリと同じサイトのタブを閉じ、通信ありで新版を読み込む操作である。

Windows Chromeの4項目が合格。付属Chromiumの同じ登録解除APIも復旧まで合格。WebKitは旧版メニューの準備・適用と合成失敗でのデータ保持まで合格したが、登録解除後の再起動の登録照合は不合格。新版表示・制御済みWorker・全資材は存在するのに登録取得が返らず、内部原因は未確定として残す。全エンジンの総合合格は宣言しない。Safari等を対象から外さず、この復旧操作の確認未完了として記録する。0.26.0のアプリソースと配信版は変更していない。

## 実機での未確認と案内

Pixel 6aのChromeの正確な不具合原因、押下後の表示、Chrome版と登録解除による復旧結果は未確認。押下後の状態を発案者へ確認中。Chromeの内部画面がこの端末で開けるかも未確認とし、PCの結果を実機の合格にしない。

手順の対象Scopeはhttps://gerupon-lgtm.github.io/prism/だけ。サイトデータ全体を消す操作へ置き換えない。復旧後に開くURLはhttps://gerupon-lgtm.github.io/prism/?recover=0.26.0。URLの変更だけでは旧Workerを回避できないため、登録解除・旧画面を閉じる操作と組み合わせる。

Chrome公式の[Service worker overview](https://developer.chrome.com/docs/workbox/service-worker-overview)と[Debug Progressive Web Apps](https://developer.chrome.com/docs/devtools/progressive-web-apps)で、内部画面と対象登録の解除を確認した。データ保持と再起動の証拠は本プロジェクトのPC実験である。

付属Chromiumのheadless shellはchrome://serviceworker-internals/を開けないため、同じ登録解除APIを使用した。実管理画面のUnregisterリンクを押す検証はインストール済みWindows Chromeで行った。内部画面の要素をボタン・専用プロパティとして探した途中不合格は、実際の表示リンクを読む方法へ直した。アプリの不具合と混同しない。
